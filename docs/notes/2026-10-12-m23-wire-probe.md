# M2.3 步骤 0：providers wire 层实测——哪些假设被推翻

日期: 2026-10-12
锚点: docs/adr/0016-providers-wire-layer.md, docs/adr/0018-prompt-blocks-and-cache-prefix.md,
      docs/adr/0017-context-records-in-transcript.md, docs/specs/behavior-context-fc.md

探针脚本是临时的（`scripts/dev/wire_probe.py`，跑完即删、不入库）；本条只留**观察到的事实**
与**因此改掉的预测**。凭据全程只在子进程内使用，未打印、未入库。

## 我原来的预测

1. 本机有可用的 Anthropic 兼容端点，能直接观测 SSE 帧、prompt cache 命中与 429 语义。
2. prompt cache 会命中：同一静态前缀 + `cache_control: ephemeral`，第二次请求的
   `cache_read_input_tokens` 应 > 0。
3. 错误响应可以用 body 里的 `type`/`code` 归一分类（FlowCoder 的 `error_mapping` 即走异常类型）。
4. FlowCoder 的权限档位名与 Questor 的三档对得上，evals 基线 adapter 直接透传即可。

## 实际观察到什么

**预测 1 被推翻，且推翻得很有信息量。** 本机唯一配置的端点是 `api.deepseek.com`
（protocol 标注 `openai-compat`），所有请求返回 **HTTP 402 `Insufficient Balance`**。
同一次探针里还拿到三条形状事实：

- `https://api.deepseek.com/v1/messages` → **404 + 空 body**（`content-length: 0`），
  而 `https://api.deepseek.com/anthropic/v1/messages` → **402 + JSON 错误体**
  ——404 说明路径不存在、402 说明路径存在只是账户没钱。判"这个端点讲不讲 anthropic 协议"，
  **状态码比 body 更可信**。
- 错误体两族同形：`{"error":{"message","type","param","code"}}`。
- 402 的 body 里 `type = "unknown_error"`、`code = "invalid_request_error"`——
  **body 的分类字段与真实原因无关**。照 body 归类会把"账户欠费"当成"请求参数错"，
  进而错误地判不可重试/可重试（402 属配额类，应当不可重试并给出人类可读原因）。
  → 落到错误分类次序：**先 HTTP 状态码，再 body 的 type/code，最后 message 关键字**。
- 对 anthropic 兼容路径发一个缺 `messages` 的 body → **422** +
  `Failed to deserialize the JSON body into the target type: missing field 'messages'`，
  且响应**没有** `retry-after` 与任何 `x-ratelimit-*` 头。也就是说：`retry-after` 必须按
  "可能不存在"实现（本地退避兜底），不能假设限流响应一定带权威等待时长。

**预测 2 未能验证**：没有一次成功响应，缓存命中与否**本轮无观测**。因此 ADR-0018 的分块与缓存
边界照写（它是接口面，与是否命中无关），但 B-81 的**证据**要等凭据可用时的实测才能落坑目录——
现在落笔就是"没有证据的断言"（AGENTS 铁律 1）。本轮只把该判据写成假服务器上的**形状断言**。

**预测 4 被推翻。** `flowcoder --mode read_only` 直接报参数错：FlowCoder 的档位是
`default | acceptEdits | plan | bypassPermissions | custom | dontAsk`（六档），
Questor 是三档（`read_only | standard | unconfined`）。evals 的基线 adapter 必须显式做
**档位映射表**（映射不承诺等价保护，与 M6 引擎权限映射表同一诚实口径），不能透传。

**顺带证伪了一条文档陈述**：`docs/plans/development-plan.md` L58 写"CI 从不跑 pyright"，
实测 `ci.yml` 的 types job 就在跑；该行已按现实回写（真缺的是生成链核查，见 ADR-0019）。

## 差异在哪、为什么

- 我的预测把"配置存在"当成"端点可用"。两者相差一个账户状态，而账户状态恰好伪装成
  4xx 业务错误——这正是 providers 错误分类要按状态码优先的原因。
- FlowCoder 用 SDK 时看不到这层：`openai.APIStatusError` 把 402 直接抛给上层
  （探针跑 FlowCoder 时也复现了：抛在 `client/core.py#L345` 的 `chat.completions.create`），
  它的 `error_mapping` 按异常类型归类，同样得不到"这是配额问题、重试无用"的结论。
  自建 wire 层至少能把"状态码 → 可重试性"写成显式表。

## 对 M2.3 的处置（不改出口判据，改达成路径）

1. providers 的实现与测试**不依赖真实端点**：wire 层用 `httpx.MockTransport` 的假服务器，
   按本轮实测到的真实形状（404 空 body、402 JSON 体、422 反序列化错、无 `retry-after`）
   写用例——本轮的失败响应反而成了最好的 fixture 来源。
2. "真实任务全链"与"evals N=12 对照基线"两项出口判据**当时被凭据阻塞**（已记账号余额，
   复测结果见下节）。
3. B-81 保持待实测；本轮先落 B-82/B-83/B-84 与"状态码优先于 body 分类"这条新坑。

## 复测（同日充值后）：真实往返拿到了，两条预测各有一半成立

同一个账户、同一组请求（静态前缀 ~3.3K token + `cache_control: ephemeral`，连发两次）：

- **拿到 200 了**。Anthropic 兼容路径 `https://api.deepseek.com/anthropic/v1/messages`：
  31 个 `event:` + 31 个 `data:` 帧（两家风格共存），`usage` **分两段到达**——
  `message_start` 带 `input_tokens=203`、`cache_read_input_tokens=3072`、
  `cache_creation_input_tokens=0`、`output_tokens=0`，后续 `message_delta` 才补上
  `output_tokens=24`。这正是 providers 里"用量分两段合并"设计的实测根据。
- **预测 2 只有一半成立，说清差别**：缓存确实命中（`cache_read_input_tokens=3072 > 0`），
  但**第一次请求就已是 3072**，且第二次数字不变——说明该端点**自动缓存前缀**并在 usage
  里如实回报，`cache_control` 不是命中的必要条件。所以 ADR-0018 的分块仍值得做（它把
  "哪段稳定"声明在内核侧，使各家机制能一致地取用），但不得声称"加了断点才有命中"。
- **新事实（直接影响预算）**：缓存命中的 3072 token 仍占窗口——只计 `input_tokens` 会
  把窗口算小、压缩阈值永远偏晚。因此 `LLMUsage.total_input()` = input+cache_read+cache_creation，
  锚点用它（B-82 的实测补充）。
- **错误形态补齐**：无效模型名 → **400**（非之前的 422）+ `type=invalid_request_error` +
  可读消息列出支持型号；仍**无** `retry-after` 与 `x-ratelimit-*`。
- **一条新坑形状**：`response.model` 与请求的型号名不必一致（anthropic 路径回
  `deepseek-v4-flash`、openai 路径回 `deepseek-flash`）——能力解析不得拿响应里的
  型号名做键（否则 B-82 的硬编码表会以另一种形式长回来）。

处置更新：上面的"真实全链/evals 基线 blocked"已解除（凭据可用）；providers 的假服务器用例
保留（它们测的是形状与失败路径，与真实往返不互为替代）。
