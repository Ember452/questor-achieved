# ADR-0007 — Windows 沙箱策略：诚实降级 + 进程树管理，强隔离走可选执行环境

状态: accepted
日期: 2026-10-11 | 关联: `overview.md` §9 §10 §12 §13、`AGENTS.md` §三（limen）、B-NN（M1 扫描补录）

## 结论

Windows 上 `standard` 档的隔离内容由三层组成，且**对外如实标注**：

1. **limen 路径门**（工具层强制，从可达性推导，唯一权威门）——写域边界的主执行者；
2. **Job Object 进程树管理**——所有命令经 Job Object 派生：超时/取消时整树硬杀、
   防孤儿进程。这是执行管理件，**不是写隔离**，任何界面与文档不得把它宣称成沙箱；
3. **敏感路径守卫**（凭据库、SSH 私钥、环境文件、凭据类 JSON 拒读写）——三档全开，
   `unconfined` 也不解除（沿用 overview §9 既有裁决）。

`standard` 档在 Windows 上**没有 OS 级写隔离**：会话创建时显式标注"仅路径门 +
进程树管理 + 敏感路径守卫"并要求一次性确认。**不实现**受限令牌 + 全盘 deny-ACL 的
自研 OS 沙箱。Docker 与远程执行环境是 L4 可选强隔离层（feature flag 默认关），
与会话档位相互独立。

**fail-closed 保留**：路径门无法施加于某次执行（如 M6 外部引擎中不可包装的执行形态）
时拒绝执行，绝不静默降级；该情形按"仅 `unconfined` 可用"标注，而不是放宽门。

macOS / Linux 平台后续接入时按 wuu 语义接 OS 级沙箱（Seatbelt / Landlock），
届时这两个平台的 `standard` 档是真 OS 隔离——Windows 的降级是**平台现实陈述，
不是永久承诺**。

## 理由与取舍

**为什么不做受限令牌 + deny-ACL（原方案②的完整版）**：

- 开发工具链系统性依赖工作区之外的合法写入（包管理缓存、工具状态在
  `%LOCALAPPDATA%` / `%APPDATA%` / `~/.cache`）。deny-by-default 必须为这些路径开洞，
  而放行清单恰好开在供应链风险最大的位置——沙箱保护被自己的便利清单抵消；
- 自研令牌/ACL 的正确性极难验证（ACE 顺序、令牌 SID 组合、每类进程行为差异），
  与三柱之"可验证"直接冲突：拿不出"沙箱确实生效"的可复验证据；
- wuu 在 Windows 上的现实选择是 fail-closed（受限模式命令工具直接失败），
  印证该路径在 Windows 上的成熟度不足以支撑日常主路径。

**保留方案②中的 Job Object**：成本一次性、收益确定（进程树生命周期控制），且与
取消传播、超时移交（overview §10）本就是同一套机制，不新增独立工程。

**为什么不让 Docker Desktop 担当 standard 档默认后端（原方案①）**：

- 引入安装依赖、常驻 VM 与每命令启动延迟，与"个人工作站、开箱即用"冲突；
- 工作区挂载与镜像内工具链维护是另一条长期成本线；
- 但它保留为 L4 可选后端——需要强隔离时由用户显式选择（与远程执行环境同层）。

**为什么选③并加码**：与铁律"透明度恒为最大，分级的是写域"同构——写域在
Windows 上由路径门划定，OS 隔离的缺席**如实告知并要确认**，绝不假装。原方案③
只说"标注 + 确认"，本 ADR 补上 Job Object 与三档全开的敏感路径守卫，把降级档位的
实际内容钉死，避免"standard 在不同平台含义漂移"。

## 被否决的选项

- **方案①全量容器化 standard 档**：见上；另违反"核心依赖保持极简"（overview §4）。
- **方案②完整版（受限令牌 + 全盘 deny-ACL）**：见上。
- **Windows Sandbox（Win11 Pro 特性）**：按会话整体重置、脚本化与自动化能力弱、
  依赖 Pro 版，不适合作为每命令隔离原语。
- **AppContainer**：默认断网 + 配置文件/命名管道重定向，普通开发 CLI 大面积损坏，
  兼容性债高于收益。

## 适用条件与失效条件

**适用**：Windows 为第一开发/使用平台；单用户本地场景；`run` 工具由本项目进程直接派生。

**触发重新评审的信号**：

1. 出现可脚本化、默认可用、对开发工具链友好的 Windows OS 沙箱原语；
2. 用户开始频繁运行不可信项目（`standard` 档需求从"防误写"升级为"防恶意"）→
   把 Docker 提升为 `standard` 档的推荐后端；
3. M6 外部引擎适配中出现无法施加路径门的执行形态 → 该引擎在 Windows 标注为
   仅 `unconfined` 可用，而不是放宽门。
