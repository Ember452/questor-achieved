# ADR-0026 — vigilia 调度与清扫语义：声明式触发器 + tick 游标幂等 + 唤醒检查点

状态: accepted
日期: 2026-10-12 | 关联: `docs/plans/development-plan.md` M4、`docs/specs/behavior-queue-ef.md`、
`docs/architecture/overview.md` §5 §10、`B-40` `B-41` `B-42` `B-44` `B-49`

## 结论

`vigilia` 承担值守长跑，语义固定为四件：

1. **声明式触发器数据**：触发类型 `once` / `interval` / `cron` 与调度参数由 schema 承载（是数据，不是分支）。
2. **tick 循环**：一个 tick 最多启动 N 个 pending；`per-task asyncio.Lock` 字典 + 守卫锁防重入
   （B-49）；并发上限进常量表。
3. **幂等与去重**：`once` 触发成功立即写 `once_fired` 幂等标记（写标记失败记 warning 但不阻塞，B-42）；
   同分钟去重单闸（B-41）；**错过不重放**（一次性任务过期即跳过）。
4. **清扫与 reconcile**：僵尸运行清扫**一批一间隔 + 游标分批**，绝不无 offset 重查同一 top-N（B-40）；
   启动 + 周期**双 reconcile**（B-44）；清扫可整体开关。

**唤醒检查点**：每次 tick 把"已推进到的游标与已触发集合"作为检查点落盘，重启后据此续跑，
而不是靠内存态；这是长跑侧对"本地时钟休眠/漂移"（B-41）的补偿机制。

## 理由与取舍

- **不重新发明**：以上是 `behavior-queue-ef.md` 从 EvoFlow 实测抽出的成熟结论，逐条对应一个 B-NN 与一条测试；
  M4 的价值在"正确重实现 + 钉住坑"，不在重新设计调度器。
- **本地时钟诚实声明**：cron 依赖本机时钟，休眠/漂移会漏触发；本项目**不假装**有分布式时钟，
  改用"检查点 + 双 reconcile + 错过不重放"这一组确定行为，并在面向用户的文档里显式声明。
- **清扫自建**：`overview.md` §3 已裁定 EvoFlow 的自愈清扫绑在框架 runs API 上、换底座即失效，
  Questor 必须自建状态机清扫；故清扫只读 `gesta`/编排 store 的落盘事实，不依赖任何框架 API。

## 被否决的选项

- **多批循环无 offset**：正是 B-40 记录的历史坑——sticky running ≥ batch 时每 0.5s 紧密空转。
- **引入 APScheduler 等第三方调度库**：新增依赖须先 ADR，且其 cron 语义与"本地时钟敏感性"声明
  并不能省掉检查点与 reconcile；本期无第二个真实使用者，`overview.md` §14 明确拒绝。
- **per-thread 锁替代全局锁**：`gesta` 热路径已为此裁决（跨进程索引一致性优先），vigilia 沿用同一口径。
- **内存态调度（不落检查点）**：重启即丢全部调度进度，与"长跑"目标直接冲突。

## 适用条件与失效条件

- **前提**：单进程宿主；本机时钟可读；调度对象是本地 run。
- **失效信号**：① 出现多宿主/分布式调度需求（远端执行环境，M8）→ 须重新评审时钟与去重模型；
  ② 检查点文件成为性能瓶颈（海量触发器）→ 改为分片检查点，须新 ADR。
