# ADR-0023 — M3 传输层只落 WS，SSE 推到 M8

状态: accepted
日期: 2026-10-12 | 关联: M3b-3 / `overview.md` §8 §12 §14、`structure.md` §7 宿主表、
ADR-0020（接口面提前）、ADR-0022（serve 传输层依赖）、B-60 B-96

## 结论

`overview.md` §8 与 `structure.md` §7 都把网页宿主传输写成 "**WS/SSE**"——本 ADR 明确
M3 只落 **WS** 一条道，SSE 推到 M8 或"出现第二类只读订阅者"时一起做。

**理由判据（overview §14 三问）**：
1. **改的代价是搬运还是重写**：WS 已能覆盖"通知扇出 + 客户端上行"；SSE 只是"单向通知"的
   轻量版。将来若加 SSE，是把 Fanout 输出接一条 `text/event-stream` 响应——**搬运级**，
   不是重写。
2. **留门只落在边界**：Fanout（M3a-3 落）就是边界；SSE 与 WS 都从 `subscribers: list[Queue]`
   消费，同形状。不做提前抽象。
3. **是否有第二真实使用者**：M3 只有浏览器一个订阅方；SSE 与 WS 的差异常来自
   "移动网络下的自动重连"与"代理链对 WS 不友好"两类，都是 M8 自托管场景。M3 无此使用者。

三问第 1、3 问都判"否"→ M3 不留 SSE。

## 理由与取舍

- **工程量与验证面**：WS 与 SSE 各一套传输适配，测面翻倍；只做 WS，M3 出口判据
  "网页 localhost 与桌面共用同一契约"已能达成。
- **B-96 的覆盖**：Fanout 顺序性用 WS 单条道就能验；引入 SSE 只是"多一条 subscriber 消费"
  不新增断言。
- **与 development-plan M3 交付表的关系**：development-plan.md L217 与 overview §12 M3 交付
  里的 WS/SSE 都属**范围说明**，不是接口面；本 ADR 把 SSE 从 M3 摘出属"有理由的偏离"
  （AGENTS §一 允许），structure §7 网页宿主行的传输列同步回写。
- **代价**：M8 自托管部署若客户环境有代理链阻断 WS，SSE 是兜底；本 ADR 的失效条件里明列。

## 被否决的选项

- **两条传输一起做（照 plan 直译 WS/SSE）**：违反三问第 3 问"无第二使用者"；工程量与验证面
  翻倍不换来接口形状的变化。
- **只做 SSE 不做 WS**：反向请求 `approval/request`（M3a-3 habena）需要双向；SSE 只能单向推
  通知，客户端回响应要走额外 POST 端点，等于两套形状并存——破 R4。
- **把 WS 也推到 M8**：M3 出口判据"网页默认只绑 127.0.0.1 且无第二套契约"要有浏览器宿主
  才能证；不能靠桌面壳（ADR-0024 桌面壳已推）。
- **在 Fanout 里预留 SSE 抽象**：属"落在抽象层上的留门"，overview §14 明令拒绝。

## 适用条件与失效条件

**适用**：M3b-3 起至 M8 之前；`structure.md` §7 网页宿主行传输列写 WS。
**触发重新评审**：① M8 自托管部署需要跨 HTTP/1.1 代理或"半双工友好"环境 → 引入 SSE 分支，
按新增依赖/新增传输走单独 ADR；② 出现第二类纯订阅消费者（如远程仪表盘）；③ 若 M6 外部引擎
适配器要求 stdio 之外的另一种单向流，届时一并做。
